# A05 Security Misconfiguration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a brand new A05 category (OWASP Top 10 2021: Security
Misconfiguration) with six genuinely exploitable examples, two per
difficulty tier, following the exact category-scaffold pattern established
by A01–A04.

**Architecture:** A new Flask blueprint
(`app/categories/a05_security_misconfiguration/`) registered in
`create_app()`, following A04's structure exactly (routes.py, models-free,
no seed_fn, one template per example extending `core/example_page_base.html`,
one `overview.html` extending `core/overview_base.html`). One example (the
Werkzeug-debugger RCE) additionally requires composing the app's WSGI
callable with `DispatcherMiddleware` in `wsgi.py`, scoped to a single URL
prefix, plus a one-line `Dockerfile` change — the only infrastructure this
plan touches outside the new category package.

**Tech Stack:** Flask, Jinja2, Werkzeug (`DispatcherMiddleware`,
`DebuggedApplication`, `werkzeug.test.Client`), pytest + Flask test client.

**Spec:** `docs/superpowers/specs/2026-09-21-owasp-lab-a05-security-misconfiguration-design.md`

## Global Constraints

- No new database models, no `seed_fn` — every example's fake sensitive
  content is either a bundled file or hardcoded in its route, matching
  A04's precedent.
- No change to any existing category's routes, templates, or tests.
- `wsgi.py`'s `app` name must stay the bare Flask object —
  `gunicorn.conf.py`'s `post_fork` hook does `from wsgi import app` and
  calls `app.app_context()`, which only exists on a real Flask app, not on
  the `DispatcherMiddleware`-wrapped composite. The composite gets a
  different name, `application`, and the Dockerfile's gunicorn CMD changes
  from `wsgi:app` to `wsgi:application` accordingly.
- `pin_security=False` is passed directly to `DebuggedApplication`'s
  constructor (live-verified to work) — no `WERKZEUG_DEBUG_PIN` environment
  variable is needed anywhere.
- The debugger sub-app (`internal_tool_app`) is a completely separate Flask
  instance with its own `DEBUG`/`PROPAGATE_EXCEPTIONS` config — the main
  app's config is never touched, so its own error handling (a plain Flask
  500 page) is untouched everywhere else.
- The CORS example's cookie (`a05_loyalty_token`) is a dedicated,
  hand-set cookie (`resp.set_cookie(..., samesite="None", secure=True)`) —
  never a change to Flask's global `SESSION_COOKIE_SAMESITE`/
  `SESSION_COOKIE_SECURE` config.
- Every illustrative payload/markup shown as static template text must have
  literal `<`, `>`, `&` written as `&lt;`, `&gt;`, `&amp;` — Jinja does not
  autoescape literal block content, only `{{ }}` expressions.
- Test assertions proving a leaked secret/executed command/bypassed check
  must never be satisfiable by the example's own static teaching prose —
  several instances of this exact risk were checked and ruled out during
  this plan's own writing; preserve that precision if anything changes
  during implementation.

def backup_file():

  foothold in a much larger breach.
</p>

DEBUG_MOUNT_PREFIX = "/internal-tools"

internal_tool_app = Flask("a05_internal_diagnostics_tool")
internal_tool_app.config["DEBUG"] = True
internal_tool_app.config["PROPAGATE_EXCEPTIONS"] = True

def diagnostics():
    # VULNERABLE: this legacy internal diagnostics tool was mounted with
    # Flask's debug mode left on. Any unhandled exception here reaches

    debugged_internal_tool = DebuggedApplication(internal_tool_app, evalex=True, pin_security=False)
    return DispatcherMiddleware(main_app, {DEBUG_MOUNT_PREFIX: debugged_internal_tool})
