This is the most severe consequence of the two bugs already shown elsewhere in this category — accepting a session id from a URL, and never rotating it on login — chained into a full attack. An attacker doesn't need to steal a password, or even observe network traffic. They only need to get you to open a link before you log in.

{% endblock %} {% block detect %}

Watch what happens to the session id across a login: visit Account, note the session ID shown, then log in and check the ID again. A secure app would show a completely different ID after authenticating — here, it's identical.

{% endblock %} {% block exploitation %}

Play both roles yourself to see the full chain:

  1. As the attacker: open this link (it plants a fixed, attacker-chosen session id) — /a07/account?sid=attacker-planted-9f8e7d. This is exactly the kind of link an attacker would email, message, or embed anywhere a victim might click it.
  2. As the victim: having just opened that link (so your browser's cookie is now that exact planted value), log in normally via Customer Login.
  3. As the attacker again: from a terminal — no browser, no cookies, nothing but the id the attacker chose in step 1 — replay: 
    curl -b "a07_session_id=attacker-planted-9f8e7d" http://127.0.0.1:5001/a07/account

It returns "Logged in as dana." The attacker is now fully authenticated as the victim, having never seen a password, a cookie theft, or any network interception at all — only a single link click by the victim, before they ever logged in.
