{% extends "core/example_page_base.html" %} {% set example_title = "Password Reset via Username Collision" %} {% set example_difficulty = "Hard" %} {% block title %}{{ example_title }} — A07{% endblock %} {% block explanation %}

This registration form accepts any username exactly as typed, including leading or trailing whitespace — "dana" and "dana " are stored as two entirely distinct accounts. The self-service "forgot my password" flow that follows registration, however, looks up which account to reset by stripping whitespace from your session's username first. If another account already exists whose username exactly equals yours after stripping, the reset lands on THAT account instead of the one you actually registered.

{% endblock %} {% block detect %}

Register an account whose username is an existing one plus a trailing space (e.g. an account you know exists, with a space appended), then use the "forgot password" flow immediately afterward — check whose password actually changes.

{% endblock %} {% block exploitation %}
  1. Register a new account with username dana (note the trailing space) and any password of your choosing, at the form below.
  2. You're automatically taken to the password reset page. Submit a new password there.

The reset flow strips whitespace from your session's username ("dana " → "dana") before looking up which account to update — and since the real, seeded dana account already exists, ITS password gets overwritten, not the one you just registered. You now control the real dana account's password without ever knowing its original password, purely by exploiting a whitespace mismatch between registration (no normalization) and password reset (normalizes before matching).

This is the same class of bug as a real-world account-takeover vulnerability in CTFd (CVE-2020-7245): register with the victim's username plus whitespace, then trigger a reset for "yourself" and let the loose matching redirect it onto the victim's real account.
