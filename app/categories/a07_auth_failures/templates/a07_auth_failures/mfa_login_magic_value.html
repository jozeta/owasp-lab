This login has a real second factor with a real, per-login generated code — hidden from you, same as this category's brute-force example. The flaw is a leftover developer/testing shortcut: the verify endpoint accepts a small set of hardcoded "magic" values as ALWAYS valid, regardless of what the real code actually is. Backdoors like this are meant to be removed before shipping and, in this lab, weren't.

{% endblock %} {% block detect %}

Before trying to guess or intercept the real code, try a handful of suspiciously common "test" values first — 000000, 111111, the literal string null — many internal test/QA bypasses use exactly these.

{% endblock %} {% block exploitation %}
  1. Log in with a valid account below (dana / welcome1).
  2. On the code-entry page — without ever learning the real code — submit 000000.

It's accepted. The verify endpoint checks the submitted code against the real per-login code OR a small hardcoded set of magic values — 000000 and the literal string null both work — completely independent of what the real code is.
