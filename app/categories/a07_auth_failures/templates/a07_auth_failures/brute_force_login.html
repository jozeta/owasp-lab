This "Customer Login" page checks a submitted username and password against a real, securely-hashed account — there's no SQL injection or logic flaw here, the check itself is correct. The vulnerability is what's missing: no limit on how many times you can guess, no delay between attempts, no lockout, no CAPTCHA. A script can try passwords exactly as fast as the server can respond.

{% endblock %} {% block detect %}

Submit a handful of wrong passwords in a row for the same username and watch the response: every single attempt gets exactly the same instant "Invalid username or password" — no slowdown, no warning, no sign the server is tracking failures at all.

{% endblock %} {% block exploitation %}

The seeded account dana uses a common, weak password. Try a short wordlist of common passwords against it: 

password
123456
welcome1
qwerty
letmein

welcome1 succeeds. In a real attack this would be scripted — hundreds or thousands of guesses per minute, limited only by network speed, because nothing on the server ever says "slow down" or "locked out."
