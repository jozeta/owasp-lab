This login also has a password step followed by a code-entry step. The bug is subtle: the pending verification code is stored keyed only by username, not by the specific session/browser that requested it. The verify page even asks you to re-enter your username alongside the code — a small but telling sign that it isn't relying on your session's own identity at all.

{% endblock %} {% block detect %}

Compare this verify page to a normal one: does it ask for a username field at all, given you're already in an authenticated-ish session at this point? If the server needs you to tell it who you are again on the verify step, it may not actually be checking that the code belongs to your session.

{% endblock %} {% block exploitation %}
  1. In one browser (or this tab), log in as dana / welcome1 below — a real code is generated and shown on the following page, keyed to the username dana.
  2. In a completely separate browser session (a different browser, an incognito window, or any session that never entered dana's password anywhere), visit the verify page and submit username dana together with that same code.

The second, completely unrelated session is authenticated as dana anyway. The code was only ever bound to a username string — never to the specific session that actually proved it knew dana's password in the first place.
