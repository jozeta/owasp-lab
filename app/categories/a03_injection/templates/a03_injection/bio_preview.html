This "preview your profile bio" feature has the exact same underlying flaw as the email preview example — it renders your submitted bio text with render_template_string(), treating it as live Jinja template source. As a "security" measure, the server first checks your submitted text against a blacklist of forbidden words (os, import, exec, eval, popen, subprocess, system) and refuses to render if any appear. This blocks the obvious payload — but it doesn't fix the actual bug, because the real problem is rendering attacker-controlled text as template source at all, not which specific words appear in it.

{% endblock %} {% block detect %}

Submit the same basic probe as the email preview example: 

{% raw %}{{ 7*7 }}{% endraw %}

This contains none of the blocked words, so it sails through the blacklist. If the preview evaluates the expression instead of showing it literally, the underlying SSTI bug is confirmed — the blacklist only filters specific keywords, not the ability to evaluate templates at all.

{% endblock %} {% block exploitation %}

The straightforward RCE payload from the email preview example is blocked here: 

{% raw %}{{ self.__init__.__globals__.__builtins__.__import__('os').popen('id').read() }}{% endraw %}

It contains the literal words os, import, and popen, so the blacklist rejects it before rendering. But Jinja2 has a ~ operator that concatenates strings inside the template expression itself — so you can build the blocked words at render time instead of writing them literally:

  1. Submit this instead: 
    {% raw %}{{ self.__init__.__globals__.__builtins__['__imp'~'ort__']('o'~'s').__dict__['pop'~'en']('id').read() }}{% endraw %}
  2. None of import, os, or popen appear as literal substrings in what you submitted — '__imp'~'ort__' only becomes the string __import__ once Jinja evaluates it — so the blacklist's substring check passes, and the exact same command execution happens as in the email preview example. The preview shows the real output of the id command.

This is the real lesson: blacklisting specific keywords is not a fix for SSTI, because the attacker doesn't need to write those keywords as literal text — only to cause the interpreter to evaluate them. Real-world "security" filters built this way (block a list of scary words) have been bypassed the same way in production Flask applications; the only real fix is to never render attacker-controlled text as template source in the first place.
