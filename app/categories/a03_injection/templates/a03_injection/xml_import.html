This "import a contact" feature accepts raw XML and parses it with lxml.etree.XMLParser(resolve_entities=True). Setting resolve_entities=True tells the parser to actually expand any external entities declared in a <!DOCTYPE> block — including ones that read arbitrary files from the server's filesystem and substitute their contents directly into the parsed document.

{% endblock %} {% block detect %}

Submit a <!DOCTYPE> declaring an external entity that reads a small, harmless file every Linux system has — /etc/hostname: 

<!DOCTYPE contact [<!ENTITY test SYSTEM "file:///etc/hostname">]>
<contact><name>&test;</name></contact>

This is a discriminating test: a vulnerable parser (resolve_entities=True) expands the entity and shows the container's hostname; a correctly hardened parser (resolve_entities=False) raises an error instead, because it never resolves external entities at all — only a vulnerable parser will show real file content here. (An internal entity like <!ENTITY test "probe-ok"> would NOT discriminate: both parsers substitute internal-subset entities regardless of resolve_entities, so it can't prove the bug exists.)

{% endblock %} {% block exploitation %}
  1. Submit the following XML: 
    <?xml version="1.0"?>
<!DOCTYPE contact [
  <!ENTITY xxe SYSTEM "file://{{ secret_path }}">
]>
<contact><name>&xxe;</name></contact>
  2. The response displays the contents of a file on the server's filesystem that this "contact name" field was never meant to expose.

XXE file disclosure has been used in the wild to read application source code, configuration files containing database credentials, and SSH private keys directly off application servers — often through features that look as innocuous as "import a spreadsheet" or "upload an XML config." Any endpoint that parses attacker-supplied XML with entity resolution enabled is a potential full-filesystem-read vulnerability.
