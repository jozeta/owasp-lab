This "employee directory search" feature has the exact same underlying flaw as the company directory login example — it builds an LDAP filter directly from your input with no escaping: (&(uid=TARGET)(description=QUERY*)). Unlike the login example, though, this feature never shows you the matched value — only whether a match exists at all, reported below as a single found / not-found result. That single bit of information, repeated many times with different inputs, is enough to extract data you were never shown: this is blind LDAP injection.

{% endblock %} {% block detect %}

Search for the root_admin account with a single-letter query: 

target: root_admin
query: r

If this reports a match, the server is treating your query as a filter fragment (a prefix match against the account's description field) rather than literal search text — the next step turns that single true/false bit into a way to read data you can't see directly.

{% endblock %} {% block exploitation %}
  1. Search with target=root_admin and query=r — the search reports a match (the hidden description value starts with "r").
  2. Try query=re — still a match. Try query=rf — no match. Keep extending the query by one character at a time, trying every letter/digit until one matches, then moving to the next position.
  3. Repeating this character by character recovers the entire hidden description value — a secret recovery code — without ever being shown it directly, purely from the found/not-found responses.

Blind boolean-based injection is what an attacker reaches for whenever an application is vulnerable but doesn't echo back the injected data directly — the same technique this lab's Blind Time-Based SQL Injection example demonstrates for SQL. It's slower than a direct data leak (each character can take dozens of guesses), but it's fully automatable: a real attack script tries every character position in a loop exactly like this, typically recovering secrets in seconds. This matters because "the app never displays the sensitive field" is often mistaken for a mitigation — it isn't, if the underlying query is still injectable.
