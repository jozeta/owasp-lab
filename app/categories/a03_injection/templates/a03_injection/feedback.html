This feedback form blocks any submission containing the literal substring <script before doing anything else with it — a real, working filter against the obvious payload. But once a submission passes that check, the app calls Python's unicodedata.normalize("NFKC", ...) on the text before rendering it, framed as a display-consistency step (collapsing fullwidth punctuation someone might paste in from a CJK input method). That normalization step runs entirely AFTER the filter has already approved the raw string.

{% endblock %} {% block detect %}

Confirm the filter works: submit the literal text <script>alert(1)</script> — blocked. Then try the exact same tag, but typed using Unicode FULLWIDTH angle brackets (U+FF1C ＜ and U+FF1E ＞) instead of the ordinary ASCII ones.

{% endblock %} {% block exploitation %}

Submit this as your feedback (using fullwidth angle brackets, not ordinary ones): 

＜script＞alert(document.domain)＜/script＞

The literal-substring filter finds no <script anywhere in this raw input — there isn't a single ordinary < character in it — so it passes straight through. The app then runs the approved text through unicodedata.normalize("NFKC", ...), which converts each fullwidth lookalike character into its literal ASCII equivalent: ＜ becomes < and ＞ becomes >. What gets rendered — and executed — is a real, ordinary <script> tag, entirely reconstructed by a step the filter never knew was coming.

This is exactly why filtering untrusted input and normalizing it are two operations that must happen in a fixed, deliberate order — any normalization, decoding, or unescaping step performed AFTER a security check can resurrect whatever that check was trying to block, no matter how thorough the check itself is against the input it actually saw.
