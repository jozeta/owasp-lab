{% extends "core/example_page_base.html" %} {% set example_title = "Second-Order SQL Injection via Department Report" %} {% set example_difficulty = "Hard" %} {% block title %}{{ example_title }} — A03{% endblock %} {% block explanation %}

This "add employee to roster" form stores a new employee's department through a completely safe, parameterized database write -- there is no SQL injection risk at the moment of writing. The bug lives somewhere else entirely: a SEPARATE "department report" feature later reads every stored department value back and re-inserts it into a BRAND NEW raw SQL query, built with plain string interpolation instead of bound parameters.

This is second-order SQL injection: the malicious payload is stored safely, sits inert in the database, and only fires when a completely different, unrelated feature reads it back and trusts it as if it were already-safe data.

{% endblock %} {% block detect %}

Add a new employee with an ordinary department name like Marketing and confirm it shows up correctly in the report below. Then think about what happens if the department VALUE itself contains SQL syntax.

{% endblock %} {% block exploitation %}

Add a new employee using the form below with the Department field set to exactly: 

NoSuchDept' UNION SELECT username, password, 0 FROM injection_accounts--

The employee is added successfully -- this write is genuinely safe, parameterized, and never touches raw SQL. Now look at the department report further down this page: the report route builds a fresh query for EVERY distinct department already in the table, including the one you just added, by directly interpolating that stored string into SELECT name, email, salary FROM a03_employees WHERE department = '<value>'. Your stored payload breaks out of that new query's string literal and UNION-selects every row of injection_accounts instead -- real usernames and plaintext passwords appear in the report, disguised as one department's employee list.

The lesson: parameterizing the WRITE gives you zero protection if a LATER, unrelated feature re-interpolates the already-stored value into a new query of its own. Every consumer of stored data needs its own parameterization -- safety doesn't travel with the data.

{% endblock %} {% block vulnerable_code %}# Safe write -- this is NOT the bug: db.session.add(Employee(name=name, email=email, department=department, salary=salary)) db.session.commit() # Unsafe read, in a completely different route, run later: for department in distinct_departments: query = f"SELECT name, email, salary FROM a03_employees WHERE department = '{department}'" report[department] = db.session.execute(text(query)).all() {% endblock %} {% block secure_code %}# Parameterize the READ too, not just the write: for department in distinct_departments: query = text("SELECT name, email, salary FROM a03_employees WHERE department = :department") report[department] = db.session.execute(query, {"department": department}).all() {% endblock %} {% block live_example %}
