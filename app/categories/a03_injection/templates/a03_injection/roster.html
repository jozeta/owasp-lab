{% extends "core/example_page_base.html" %} {% set example_title = "Employee Roster Sort (ORDER BY Injection)" %} {% set example_difficulty = "Medium" %} {% block title %}{{ example_title }} — A03{% endblock %} {% block explanation %}

This "sort the employee roster" feature lets you pick which column to sort by, and builds the query's ORDER BY clause directly from your input with no validation: SELECT id, name, email, department FROM a03_employees ORDER BY {{ '{sort}' }}. Every other SQL injection example in this lab injects into a WHERE clause; this one is different — an ORDER BY target is a column reference or expression, not a literal value, so the usual fix (bound parameters, which only substitute literal values into a query) doesn't apply here at all. The real-world fix for this specific clause type is different too — see Vulnerable vs. Secure below.

{% endblock %} {% block detect %}

Submit an out-of-range column position as the sort target, e.g. sort=99. The roster only selects 4 columns, so ORDER BY 99 is invalid — a properly parameterized query couldn't be tricked into treating your input as a raw ordinal position at all, but this one throws a real database error, confirming your input reaches the ORDER BY clause unescaped.

{% endblock %} {% block exploitation %}
  1. Try sort=4 — the roster still loads normally (4 is a valid column position; the table selects exactly 4 columns).
  2. Try sort=5 — the request fails with a database error. That single comparison confirms the exact column count (4) without ever seeing a row of data — the same "binary search the column count" technique attackers use before pivoting an ORDER BY injection into a full UNION-based extraction.
  3. Once you don't even want to trigger visible errors, you can extract a boolean signal purely through row order. Try: sort=(CASE WHEN (1=1) THEN id ELSE id * -1 END) — the roster sorts normally (ascending by ID). Now try: sort=(CASE WHEN (1=2) THEN id ELSE id * -1 END) — the entire order reverses. Swap 1=1/1=2 for any real condition (e.g. a subquery testing a specific employee's salary) and the row order itself becomes a true/false oracle, leaking one bit per request with zero errors and zero extra data shown.

ORDER BY injection rarely gets its own headline the way UNION or authentication-bypass injection do, but it shows up constantly in real applications with sortable tables, reports, and admin grids — and it's a favorite reconnaissance step precisely because it's silent: no error, no extra column, just a reordering an attacker controls. Column counts and type information learned this way are exactly what's needed to craft a working UNION-based payload against the very same query.
