This version of the "continue" feature adds a check: the destination URL's parsed hostname must START WITH trusted-partner.example, this app's one approved external redirect target. This genuinely blocks an unrelated external URL.

{% endblock %} {% block detect %}

Confirm the filter works: try ?next=https://evil.example.com/ -- rejected. Now think about what "the host starts with the trusted string" actually checks, versus what it was meant to check.

{% endblock %} {% block exploitation %}

The check only tests whether the URL's parsed hostname STARTS WITH trusted-partner.example -- not that the host genuinely IS that domain (or a real subdomain of it). Submit: 

?next=https://trusted-partner.example.evil.example.com/phish

The URL's REAL host, trusted-partner.example.evil.example.com, genuinely begins with the characters trusted-partner.example, so the prefix check passes -- but that full string is the actual host, a domain entirely under the attacker's control (trusted-partner.example is merely a label they chose to put first). The redirect goes to the attacker's server, not the real trusted partner.

This is the classic "prefix allowlist" mistake: checking host.startswith(trusted_domain) instead of comparing the parsed host for genuine equality (or confirming it's a real subdomain, e.g. ends with .trusted-partner.example). Any hostname that simply begins with the same characters -- regardless of what follows -- slips through.
