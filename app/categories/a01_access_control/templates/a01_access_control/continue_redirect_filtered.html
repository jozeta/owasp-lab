This version of the "continue" feature adds a check: the destination URL must contain trusted-partner.example, this app's one approved external redirect target. This genuinely blocks an unrelated external URL.

{% endblock %} {% block detect %}

Confirm the filter works: try ?next=https://evil.example.com/ -- rejected. Now think about what "contains the substring" actually checks, versus what it was meant to check.

{% endblock %} {% block exploitation %}

The check only tests whether trusted-partner.example appears ANYWHERE in the URL string -- not that it's genuinely the URL's host. Submit: 

?next=https://trusted-partner.example.evil.example.com/phish

This string contains trusted-partner.example as a literal substring (right where the filter looks for it), so the check passes -- but the URL's REAL host is trusted-partner.example.evil.example.com, a domain entirely under the attacker's control (trusted-partner.example is merely a subdomain label they chose to include). The redirect goes to the attacker's server, not the real trusted partner.

This is the classic "substring allowlist" mistake: checking if trusted_domain in url instead of genuinely parsing the URL and comparing its actual host. The same bug family affects startswith() checks bypassed by a matching subdomain prefix, and any check that doesn't parse the URL structure before comparing.
