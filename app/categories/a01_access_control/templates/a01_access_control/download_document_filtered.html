This version of the document download feature adds a filter: any name containing the substring ".." is rejected outright before the file is ever opened. This genuinely blocks the classic relative-traversal technique from the sibling "Arbitrary File Read" example in this same group.

{% endblock %} {% block detect %}

Confirm the filter works: try ?name=../../../../etc/passwd — blocked. Now think about the OTHER technique from that sibling example — does it contain the substring ".." anywhere at all?

{% endblock %} {% block exploitation %}

The filter only ever checks for the literal substring "..". It never considers that os.path.join()'s absolute-path override doesn't involve ".." in any form: submit ?name=/etc/passwd — a bare absolute path, containing zero dots or slashes-in-sequence that the filter is looking for. It sails through the check untouched and reaches the exact same unguarded open() call as the unfiltered sibling example.

Blacklist filters that enumerate "the obvious" attack shape are a recurring, genuinely dangerous real-world pattern throughout this lab (the newline-bypass in this app's command-injection filter example is the same story) — a filter has to anticipate every equivalent way to achieve the same outcome, not just the first one that comes to mind.
