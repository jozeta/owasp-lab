The "Webhook Tester" example proved this feature reaches an internal endpoint and shows you what's there. Here's a different use of the exact same mechanism: submitting URLs at different internal ports produces genuinely different, distinguishable responses -- letting an attacker map which internal services exist without ever seeing a byte of their actual protocol traffic.

{% endblock %} {% block detect %}

No new vulnerable code exists for this example -- it's the same unrestricted fetch from the Webhook Tester, used differently.

{% endblock %} {% block exploitation %}

Go to the Webhook Tester and submit a couple of different internal addresses:

  • http://127.0.0.1:5000/a10/internal/metadata -- a real HTTP service, responds with content.
  • http://127.0.0.1:9999/ -- nothing is listening at all, and the connection is refused immediately.

Two different outcomes, two different facts learned about the internal network -- all through a feature that was only ever supposed to test a webhook URL.
