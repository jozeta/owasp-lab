This "forgot password" form builds the password-reset link it shows you (this lab doesn't send real email — the link is displayed directly, same as elsewhere in this app) using the Host header the request claims to have arrived on, preferring X-Forwarded-Host when present — a common pattern for apps sitting behind a reverse proxy that needs to know its own public hostname. Neither header is validated against a fixed, trusted list of real domains.

{% endblock %} {% block detect %}

Send the same request twice with a different Host header each time and compare the generated reset link — if the link's domain changes to match whatever you sent, the app trusts client-supplied host information for something security-sensitive.

{% endblock %} {% block exploitation %} 
curl -X POST http://127.0.0.1:5001/a04/forgot-password \
  -H "Host: attacker.evil.test" \
  -d "email=victim@owasp-lab.local"

The generated reset link now points at http://attacker.evil.test/a04/reset-password-confirm?token=... instead of the real application. In a real deployment behind a reverse proxy, X-Forwarded-Host is trusted the same way and is often even easier to forge than Host itself: 

curl -X POST http://127.0.0.1:5001/a04/forgot-password \
  -H "X-Forwarded-Host: attacker.evil.test" \
  -d "email=victim@owasp-lab.local"

If a real victim's password-reset email had been built this way and they clicked the poisoned link, their reset token would be sent straight to the attacker's own server — via the token in the query string, the same class of leak the referrer-header example in A02 demonstrates by a different route — instead of the real site, handing the attacker a fully working password-reset flow for that victim's account.
