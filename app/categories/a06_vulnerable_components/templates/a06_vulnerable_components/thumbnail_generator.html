{% extends "core/example_page_base.html" %} {% set example_title = "ImageTragick RCE via Image Upload" %} {% set example_difficulty = "Medium" %} {% block title %}{{ example_title }} — A06{% endblock %} {% block explanation %}

This "generate a thumbnail" feature accepts an uploaded image and shells out to a real, vendored ImageMagick build to resize it. That build is ImageMagick 6.9.2-10 -- the last release before CVE-2016-3714 ("ImageTragick") was fixed in 6.9.3-10. ImageMagick's own delegate mechanism can be tricked into shelling out to an external command when it processes a crafted file, and this feature performs zero validation of the uploaded file's actual content before handing it to that real, unpatched binary.

Upload an ordinary photo first and confirm a thumbnail is generated normally. Then think about what ImageMagick actually does when it reads a file: does it trust the filename's extension, or does it look at the file's real content to decide how to parse it?

Upload a file named poc.jpg containing the following (this is Magick Vector Graphics script, not a real photo): 

push graphic-context
viewbox 0 0 640 480
fill 'url(https://example.com/image.jpg"|id > /tmp/a06_imagetragick_proof.txt;false")'
pop graphic-context

ImageMagick detects the real MVG content regardless of the misleading .jpg extension. Processing this "image" makes ImageMagick's HTTPS delegate shell out to curl with the crafted string embedded in its command line -- the injected id > /tmp/a06_imagetragick_proof.txt genuinely executes on the server, and the proof file's real content (this server's actual id output) is shown below after you upload the payload.

This is a real, historical, extremely famous CVE (assigned a name, ImageTragick, and its own dedicated advisory site) — not a contrived training-only bug. The same delegate mechanism has other variants (different coders, different shell metacharacter tricks); this is the original 2016 proof-of-concept.
