This "check warehouse inventory" feature has verbose error reporting left on: whenever the (simulated) warehouse database connection fails, the full exception message and Python traceback are rendered directly in the response, instead of a generic error message.

{% endblock %} {% block detect %}

Submit any SKU. The lookup always fails (this demo simulates a permanently-unreachable warehouse system), and the response includes far more than "something went wrong" — read what comes back.

{% endblock %} {% block exploitation %}
  1. Submit any SKU value, e.g. SKU-001.
  2. The error message includes the full connection string the app was using to reach the warehouse database — including its password.
  3. That single leaked value is often enough to pivot directly into an internal system the attacker would otherwise have no path to.

Verbose error reporting is convenient during development — it's exactly what a developer wants to see while debugging locally. The misconfiguration is leaving it turned on once the application is actually serving real traffic, where every visitor becomes a potential attacker reading the same detail a developer would.
