This site's nightly backup script writes a full database dump to a predictable, web-accessible filename inside the same directory the application serves from — db_backup_<date>.sql.bak — with no authentication check on that path at all. Anyone who guesses (or scans for) the filename pattern can download it directly.

{% endblock %} {% block detect %}

Automated backup files are one of the first things a real attacker scans for, using predictable name patterns (.bak, .sql, .old, dated filenames) against common web roots. Here, simply requesting /a05/backups/db_backup_2024-01-15.sql.bak directly — no login, no special request — returns the file.

{% endblock %} {% block exploitation %}
  1. Visit /a05/backups/db_backup_2024-01-15.sql.bak directly.
  2. The response is the raw backup file — a full database connection string (with a real-looking password), a payment-processor secret key, and a session-signing secret, all in plain text.
  3. Any one of those three values alone would be enough for an attacker to pivot further: the database URL grants direct DB access, the Stripe key grants payment-API access, and the session secret lets an attacker forge valid session cookies for any user.

Leftover backup, config, and log files in web-accessible directories are a routinely-exploited real-world pattern — automated scanners (including tools attackers run continuously against the whole internet) specifically look for common backup extensions and naming conventions, because this exact mistake happens constantly: a script writes a backup "temporarily" to a path that was never meant to be public, and it's simply never cleaned up or moved outside the web root.
