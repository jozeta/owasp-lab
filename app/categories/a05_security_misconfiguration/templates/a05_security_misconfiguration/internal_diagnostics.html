A legacy internal diagnostics tool is mounted on this same server at /internal-tools/diagnostics, separately from the main application. It was never properly decommissioned, and it still runs with Flask's debug mode enabled — meaning any unhandled error there drops a visitor straight into Werkzeug's interactive debugger, a live Python console running inside the server process.

{% endblock %} {% block detect %}

Visit /internal-tools/diagnostics directly. Instead of a normal error page (or this app's own styling at all), you'll land on Werkzeug's raw debugger — dramatically different from anything else in this app, itself a strong signal that debug mode was left on somewhere it shouldn't be.

{% endblock %} {% block exploitation %}
  1. Visit /internal-tools/diagnostics — it always raises an error, dropping you into the interactive debugger.
  2. Click on the bottom-most stack frame (inside the diagnostics() function) to open its inline console.
  3. Type a Python expression into the console and press Enter — for example: __import__('subprocess').check_output(['id']).decode()
  4. The console runs it for real, inside the actual server process, and shows you the output — this is genuine remote code execution, not a simulation. A real attacker could read any file the server process can read, exfiltrate the database credentials, or pivot further into the network from here.

Leaving an interactive debugger reachable in a live deployment is one of the single most severe misconfigurations possible — it isn't a path to code execution, it is code execution, handed directly to whoever finds the URL. This exact mistake (a debug-mode console left reachable) has been the root cause of real production compromises.
